# ADR-0013: 契约按意图分级;确定性可判的归门禁,不进评测

- 状态:已采纳(2026-11-16)
- 关联:ADR-0012

## 背景

要讲清楚"如何控制生成漂移",需要能回答:**给 agent 的哪些信息,压住了哪一类漂移**。
这要求同一份契约可以按"传达了多少设计意图"呈现为不同版本,逐个接上去跑同一组任务。

同时,不是所有漂移都值得用 agent 评测去测:写死色值、编造 props、用了废弃入口,
这些用 lint 和类型检查就能百分之百判定,为它们设计评测用例是浪费。

## 决策

### 1. 一份数据,按字段分级

每个字段只属于一个意图级别,定义在 `packages/contract/intent-levels.json`:

| 级别 | 内容 | 数据现状 |
|---|---|---|
| `structure` | 名字、类型、值、引用关系、props 签名、生命周期状态 | 已有 |
| `description` | 一句话说明:这个 token / prop 是干什么的 | 待编写 |
| `rules` | 用途标签、规则、配对、何时用何时不用、无障碍要求 | 待编写 |
| `examples` | 精选正例、组合配方、反例 | 待编写 |

源文件里放全部字段;消费方通过 `loadContract({ level })` 读取,只拿到该级别及以下的字段。
高级别包含低级别,于是相邻两级的差异是一组已知字段,效果可以归因。
没有登记级别的字段无法通过校验——新字段必须先决定它属于哪一级。

不手写多份数据:多份手写数据之间自己会先漂移。

### 2. 门禁与评测的分工

| 漂移类型 | 归属 | 手段 |
|---|---|---|
| 值漂移(写死 hex / px) | 门禁 | lint |
| API 漂移(编造 props、废弃入口) | 门禁 | 类型检查 + 禁用废弃项 |
| 主题漂移(暗色下坏掉) | 门禁 | 禁止直接使用 base 层 token |
| 组件内部样式 | 不存在 | 组件自己封装,agent 碰不到 |
| 选错组件 / 选错变体 | **评测** | 任务 × 级别 × 多次运行 |
| 组件之间的组合与间距 | **评测** | 同上 |
| 语义角色用错 | **评测** | 同上 |
| 缺口处理(无现成组件时) | **评测** | 同上 |

`structure` 级是门禁的数据来源,也是所有评测对照组共有的底座,本身不是实验变量。
评测对照组为:仅 structure → 加 description → 加 rules → 加 examples。

### 3. structure 级的字段

- token:`name`、`cssVar`(或 `customMedia`)、`path`、`type`、`tier`、`group`、`condition`、
  `value`(已解析)、`alias`(整个值指向另一个 token)、`refs`(复合值里引用的 token);
  随模式变化的 token 按模式各给一份 `value` / `alias` / `refs`
- 组件:`id`、`name`、`importPath`、`status`、`passthroughElement`、
  `props`(`name` / `type` / `required` / `defaultValue` / `deprecated`)、`subcomponents`、`types`

`status` 与 `deprecated` 放在 structure 级:它们是枚举事实,且门禁需要它们。
"废弃后该换成什么"是意图,属于 `rules` 级。

### 4. 十个组件的选择

评测要测的是"结构对但意图错",所以组件按**容易混淆的成对关系**和**需要判断的变体**来选:

| 组件 | 测什么 |
|---|---|
| Button | 变体选择(默认 / 主要 / 危险 / 隐形 / 链接) |
| TextInput + FormControl | 组合关系;标签、说明、校验信息的位置 |
| Dialog | 底部按钮的顺序与主次、危险操作确认 |
| Dialog(已废弃的旧版) | 门禁必须能把它和新版区分开 |
| Banner + InlineMessage | 成对混淆;语义状态 |
| ActionMenu + Select | 成对混淆:动作菜单还是取值选择 |
| Stack | 组件之间的间距与布局——agent 唯一还会手写 token 的地方 |

## 备选方案

- 五级(把值和结构再拆开)——值与结构都由门禁覆盖,拆开不产生可测的差异
- 只做最完整的一份数据——能用,但无法归因,只能说"接了 MCP 变好了"
- 每个级别各存一份文件——等于把同一事实写四遍;改为源里存全量、读取时裁剪

## 后果

- 校验(`scripts/validate.mjs`)面向源文件:形状、命名、引用存在、别名与目标取值一致、
  每个字段都有级别;测试另外断言 structure 视图里不出现任何更高级别的字段
- 每个高级别字段将来都需要至少一个"没有它就会做错"的评测任务;删掉某字段后没有任务变红,
  说明字段无效或测试有缺口
- 模型的先验会抬高"无上下文"基线:通用的组件名和常见的 token 词汇,模型不看契约也能猜对
  一部分。对策是让任务落在 Lima 特有的事实上——`--lima-` 前缀、导入路径、废弃关系,
  以及 `rules` 级里 Lima 自己的规则
- 意图不是越多越好:级别越高,每次调用消耗越大,`examples` 级还可能导致照抄。
  评测的结论应是一条"收益—成本"曲线
